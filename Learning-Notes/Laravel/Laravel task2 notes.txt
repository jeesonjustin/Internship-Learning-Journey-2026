7. MIGRATION — up() AND down()

A migration normally contains:

public function up()
{
// Create or modify database structure
}

public function down()
{
// Reverse the migration
}

up()
→ Runs the migration.

down()
→ Reverses the migration.

Example:

public function down()
{
Schema::dropIfExists('student_registrations');
}

This removes the table when the migration is rolled back.

9. WHY MOBILE IS STRING

We used:

$table->string('mobile');

instead of:

$table->integer('mobile');

Reason:

A mobile number is an identifier, not a mathematical value.

We normally don't perform calculations such as:

9876543210 + 1

on a phone number.

Phone numbers may also contain:

+91
leading zeros
spaces
other formatting

Therefore:

Phone number → generally store as STRING.

10. UNIQUE EMAIL

Migration:

$table->string('email')->unique();

unique() means:

The database should not allow two records with the same email.

Example:

John → john@gmail.com
Alex → alex@gmail.com

Allowed.

But:

John → john@gmail.com
Alex → john@gmail.com

Not allowed.

unique() is a database-level constraint.

# 14. ELOQUENT ORM

Eloquent is Laravel's ORM.

ORM stands for Object-Relational Mapping.

Eloquent allows us to work with database records using PHP objects instead of writing SQL queries manually for every database operation.

For example, instead of manually writing:

SELECT * FROM student_registrations;

we can use:

StudentRegistration::all();

Another example is deleting a student.

Instead of manually writing:

DELETE FROM student_registrations WHERE id = ...;

we can use:

$student->delete();

The basic idea is:

Eloquent
    ↓
PHP syntax
    ↓
Database operations

Eloquent acts as the bridge between our Laravel/PHP code and the database.

# 15. $FILLABLE AND MASS ASSIGNMENT

In the StudentRegistration model, we used the $fillable property.

Model:

app/Models/StudentRegistration.php

Code:

protected $fillable = [
    'name',
    'email',
    'mobile',
    'course',
];

This is related to mass assignment protection.

Later, we use:

StudentRegistration::create($validated);

Here, $validated contains multiple fields that we want to insert into the database at once.

The $fillable property tells Laravel:

"These fields are allowed to be assigned through mass assignment."

Therefore:

StudentRegistration::create($validated);

can safely assign these fields:

name
email
mobile
course

Without understanding $fillable, Model::create() may result in a mass-assignment error.

required

required

# 43. UPDATE DOES NOT CREATE A NEW RECORD

Suppose the database contains:

ID: 5
Name: Alexander

After editing:

ID: 5
Name: Alexander Updated

The ID remains 5.

The existing database row is updated.

It does NOT create:

ID: 6
Name: Alexander Updated

This is an important difference between CREATE and UPDATE.

CREATE creates a new record.

UPDATE modifies an existing record.


------------------------------------------------------------

# 44. EMAIL UNIQUE RULE DURING UPDATE

For creating a student, we use:

'email' => 'required|email|unique:student_registrations,email'

This works because a new student's email must not already exist.

However, during an update, suppose:

ID 5
Email: alex@gmail.com

If we simply say:

Email must be unique.

Laravel could find:

alex@gmail.com

already exists and reject the update.

But that email belongs to the same student.

Therefore, during update, we use:

use Illuminate\Validation\Rule;

and:

'email' => [
    'required',
    'email',
    Rule::unique('student_registrations', 'email')->ignore($id),
],

This means:

"The email must be unique, but ignore this student's own record."

Example:

Updating ID 5 with:

alex@gmail.com

→ Allowed.

Updating another student's record with:

alex@gmail.com

→ Rejected.

Using:

Rule::unique(...)->ignore($id)

is cleaner and more readable for update validation.


------------------------------------------------------------

# 45. UPDATE VALIDATION SHOULD MATCH CREATE VALIDATION

Our Create validation is:

'name' => 'required|string|max:255',

'email' => 'required|email|unique:student_registrations,email',

'mobile' => 'required|digits:10',

'course' => 'required|string|max:255',

Our Update validation follows the same general rules:

'name' => 'required|string|max:255',

'email' => [
    'required',
    'email',
    Rule::unique('student_registrations', 'email')->ignore($id),
],

'mobile' => 'required|digits:10',

'course' => 'required|string|max:255',

The only important difference is the email rule.

During creation:

Email must be unique.

During updating:

Email must be unique,
but ignore the current student's existing email.

The reason for keeping the other rules consistent is that the application's business rules should remain the same when creating and editing a student.

# 66. ROUTE MODEL BINDING — NEXT LARAVEL CONCEPT

We started learning Route Model Binding as an additional Laravel refinement.

The current approach is:

public function edit($id)
{
    $student = StudentRegistration::findOrFail($id);

    return view('student_registrations.edit', compact('student'));
}

Laravel can automatically resolve the model.

Route:

Route::get(
    '/student-registrations/{student}/edit',
    [StudentRegistrationController::class, 'edit']
)->name('student-registrations.edit');

Controller:

public function edit(StudentRegistration $student)
{
    return view('student_registrations.edit', compact('student'));
}

Laravel sees:

{student}
    ↓
StudentRegistration $student
    ↓
Automatically find matching model

This removes repetitive:

StudentRegistration::findOrFail($id);

Route Model Binding is an important Laravel feature, but the core CRUD task can be understood without it.

# 67. IMPORTANT DIFFERENCE: CREATE FORM VS CREATE DATABASE RECORD

The word "create" can be confusing because it is used in two different contexts.

create() is a controller method.

public function create()
{
    return view(...);
}

It displays the registration form.

But:

StudentRegistration::create($validated);

creates a database record.

Therefore:

create()
→ Show form


Model::create()
→ Insert database record

These are two different operations.

# 68. IMPORTANT DIFFERENCE: EDIT VS UPDATE

edit()

→ Displays the edit form.


update()

→ Actually changes the database record.


Therefore:

edit()
→ GET form


update()
→ PUT data

# 69. IMPORTANT DIFFERENCE: DELETE CONFIRMATION VS DELETE

JavaScript:

confirm()

only asks the user for confirmation.

It does NOT delete the database record.

The controller method:

destroy()

actually performs the deletion.

Therefore:

confirm()
→ User interface protection


destroy()
→ Database operation

# 72. WHY VALIDATE BEFORE DATABASE INSERT?

User input cannot automatically be trusted.

Validation helps ensure:

- Required fields exist.
- Email has the correct format.
- Email is unique.
- Mobile contains exactly 10 digits.
- Name and course have appropriate data types and lengths.

General principle:

USER INPUT
    ↓
VALIDATE
    ↓
PROCESS
    ↓
DATABASE

Not:

USER INPUT
    ↓
DATABASE

Always validate incoming data before processing and storing it.

# 73. WHY USE ELOQUENT INSTEAD OF RAW SQL?

Eloquent provides an object-oriented way of working with the database.

Instead of repeatedly writing SQL such as:

SELECT
INSERT
UPDATE
DELETE

we can use:

StudentRegistration::all();

StudentRegistration::create();

$student->update();

$student->delete();

Advantages of Eloquent include:

- Cleaner Laravel code.
- Easier to read.
- Integrates naturally with models.
- Reduces repetitive SQL.
- Supports relationships and many other ORM features.

# 79. GOLDEN RULES TO REMEMBER

1. Route decides WHERE the request goes.

2. Controller decides WHAT should happen.

3. Model/Eloquent communicates with the database.

4. Migration defines the database structure.

5. Blade displays the data/UI.

6. Validate user input BEFORE saving it.

7. Use $fillable when using mass assignment.

8. Use named routes instead of hard-coded URLs.

9. Use @csrf for state-changing forms.

10. Use @method('PUT') for update forms.

11. Use @method('DELETE') for delete forms.

12. create() displays the creation form.

13. Model::create() creates a database record.

14. edit() displays the edit form.

15. update() modifies an existing record.

16. destroy() deletes an existing record.

17. findOrFail() finds a record or returns 404.

18. @forelse handles both records and empty collections.

19. old() preserves previous form input after validation failure.

20. Laravel validation is server-side and should not be replaced by browser validation.

21. POST/Redirect/GET helps avoid duplicate form submissions.

22. Phone numbers are generally better stored as strings.

23. Database unique constraints and Laravel validation are related but not identical.

    Validation:
    → Gives the user a friendly error.

    Database constraint:
    → Provides database-level protection.

24. Blade layouts prevent repeated HTML/Bootstrap code.

25. The most important thing is understanding the:

REQUEST
   ↓
ROUTE
   ↓
CONTROLLER
   ↓
MODEL
   ↓
DATABASE
   ↓
VIEW

flow, not memorizing code line-by-line.
